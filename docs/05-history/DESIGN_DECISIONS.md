## ✅ 已确认的决策

### 决策 1：多目标同步 - 支持
**决策时间**：2026-09-08
**决策内容**：
- ✅ 支持一个 Skill 同时同步到多个 Target
- 实现方式：`skill-registry project add drawio --target claude-code,cursor`
- 同步时会创建多个软链接，指向同一个 Skill 缓存

**理由**：
- 提高灵活性，支持跨智能体使用同一 Skill
- 节省存储空间，多个链接指向同一份 Skill 内容
- 符合"以不变应万变"的设计理念

---

### 决策 2：全局项目与一般项目统一
**决策时间**：2026-09-08
**决策内容**：
- ✅ 全局项目与一般项目使用完全相同的管理机制
- 唯一区别：项目根路径不同
  - 一般项目：`/path/to/project`
  - 全局项目（家目录）：`~`（即 `/Users/numbero`）

**理由**：
- 简化概念模型，降低学习成本
- 统一的工作流程和命令
- 家目录只是一个特殊的项目路径

**实现影响**：
- 移除 `type: global` 概念
- 在家目录也可以执行 `skill-registry project init`
- 在家目录管理的 Skills 通过特定 Target（如 `claude-code-home`）同步到 `~/.claude/skills`

---

### 决策 3：Skill 格式标准
**决策时间**：2026-09-08
**决策内容**：
- ✅ 完全支持 Claude Code 的 Skill 标准（SKILL.md）
- ✅ 遵循业界通用的 Agent Skills 开放标准
- ❌ 不做个性化适配（如 Cursor 的 .mdc 格式转换）

**理由**：
- 保持简单，避免引入格式转换的复杂性
- 遵循标准，推动生态统一
- 让智能体自己兼容标准，而非工具做适配

**实现影响**：
- Target 配置中的 `format` 字段仅用于信息展示
- 同步时直接复制/链接 SKILL.md 文件，不做格式转换
- 如果某个智能体需要不同格式，用户需自行准备对应格式的 Skill

## 1. 注册表机制实现细节

### 1.1 Git 仓库克隆策略

**决策点**：当注册一个来自 Git 仓库的 Skill 时，如何克隆仓库？

**选项**：
- [ ] **A. 浅克隆（推荐）**：只克隆最新 commit，depth=1
  - 优点：速度快，节省空间
  - 缺点：无法回退到历史版本
  
- [ ] **B. 全克隆**：克隆完整历史
  - 优点：支持版本回退
  - 缺点：占用空间大，克隆慢
  
- [ ] **C. 单文件下载**：不克隆仓库，只下载 SKILL.md 和必要文件
  - 优点：最快，最节省空间
  - 缺点：无法获取资源文件，无法用 git pull 更新

### 1.2 Skill 缓存更新策略

**决策点**：用户执行 `skill-registry registry update` 时，如何更新缓存的 Skill？

**选项**：
- [ ] **A. 直接 git pull**：在原目录执行 `git pull`
  - 风险：可能有未提交的本地修改冲突
  
- [ ] **B. 删除重新克隆**：删除旧缓存，重新克隆
  - 优点：干净，无冲突
  - 缺点：慢，可能丢失本地调试修改
  
- [ ] **C. 智能更新**：检查是否有本地修改，提示用户选择
  - 有修改 → 询问是否覆盖
  - 无修改 → git pull

## 2. Skill 唯一性和冲突处理

### 2.1 Skill 唯一性标识

**决策点**：如何判断两个 Skill 是否相同？

**选项**：
- [ ] **A. 按 name 唯一**：
  - 同名 Skill 不能同时存在
  - 注册同名 Skill 时，提示覆盖或取消
  
- [ ] **B. 按 source URL 唯一**：
  - 同一个 Git URL 或本地路径只能注册一次
  - 允许存在同名但来源不同的 Skill
  - 例：可以有两个叫 "drawio" 的 Skill，一个来自本地，一个来自 Git

- [ ] **C. 按 name + source 组合唯一**：
  - 同名同源才算重复
  - 最灵活，但管理复杂

## 3. Skill 更新和版本管理

### 3.1 版本检测机制

**决策点**：如何判断 Git 仓库中的 Skill 是否有更新？

**选项**：
- [ ] **A. 检查远程 commit hash**：`git ls-remote` 获取最新 hash，与本地比较
  - 优点：准确
  - 缺点：需要网络请求
  
- [ ] **B. 直接 git pull**：不检查，直接拉取
  - 优点：简单
  - 缺点：即使没有更新也会执行 git pull
  
- [ ] **C. 用户手动触发**：不自动检测，用户自己决定何时更新

### 3.2 多版本支持

**决策点**：是否支持一个 Skill 的多个版本？

**选项**：
- [ ] **A. 不支持**：每个 Skill 只有一个版本（最新的）
